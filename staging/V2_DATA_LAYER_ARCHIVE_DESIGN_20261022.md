# 打卡系統 V2｜原系統延伸成 LINE 人資自助平台：資料分層與歷史封存方案
日期：2026-10-22。**架構草案／開發分支，非正式部署，無任何資料搬移。**

## 一、為什麼修改方向

- 使用者的正式 Google Sheet `LINE打卡系統` 已有：員工資料、上班地點、打卡紀錄、打卡紀錄_歷史、補打卡申請、請假申請、假別設定、管理者名單、審核通知名單。
- 已有正式 LINE 上下班打卡、補打卡、請假、個人三個月查詢及主管 LINE 通知／核准。這些**沿用**，不是重建。
- 使用者已在原正式 Apps Script「觸發條件」確認 **沒有已安裝觸發器**。10/20 提供的原完整後端中也未見 `打卡紀錄_歷史` 的搬移／封存程式。故自動封存是否實際運作 **尚未證實**；不可宣稱已封存，更不得清除正式資料。
- 下一步期望從 LINE 平台延伸成薪資、特休、請假歷史與出勤自助查詢。因此不應把所有年度的明細與敏感薪資資料無限制累積在當期作業 Sheet。

## 二、建議的三層資料架構（保持既有 LINE 入口）

### A｜當期作業資料庫（延用 `LINE打卡系統`）

資料：
- `員工資料`：員工 ID、LINE 綁定、公司部門、在職狀態。
- `上班地點`：GPS 中心點及容許距離。
- `打卡紀錄`：開放查詢當月＋前兩個**完整日曆月**的明細，並保留所有尚未完成月結的資料，不為了保持三個月而刪除未結資料。
- `補打卡申請`、`請假申請`：尚未核定、未完成薪資／假勤結算或未來有效的申請。已結案且已結算之舊期案件移往年度歷史庫（待設計審核後撤回、補核准等更正流程）。
- `假別設定`、`管理者名單`、`審核通知名單`：沿用，不重新建表。原主管名單 C/D = 通知文字，E = 審核主管／發核准卡；必須由後端每次核對 E 本人的 LINE 身分。
- 建議增加非業務資料 `封存控制` 或獨立封存設定資料，用來表明「哪個月份已結算」，但不能改壞既有資料範圍與格式。
- 對 LINE 查詢僅透過安全 Apps Script API，不直接共享 Google Sheet 連結給員工。

### B｜年度歷史資料庫（新建每年一個、唯讀為主）

命名例：`LINE人資歷史_2026`、`LINE人資歷史_2027`，由打卡專用 Google 帳號持有。

各年工作表分開保存：
- `打卡紀錄_歷史`：**原 11 欄**逐筆保留。
- `補打卡申請_歷史`：**原 13 欄**完整保留申請、審核狀態／人／時間。
- `請假申請_歷史`：**原 12 欄**保留申請與核准，涵蓋已辦妥的事、病、特休、公、婚、喪假。
- `特休異動_歷史`：以交易式異動紀錄保留給假、請假扣除、取消復回、到期及人工更正；不只存某一時點的餘額。
- `月份摘要`（建議）：每個員工／年月的上、下班數量、核定補卡、已核准請假時數及封存版本。
- `封存批次紀錄`：期間、原／歷史筆數、識別碼檢核、執行時間、結果與備份位置。

**本年度跨期查詢**由 API 依月份索引去該年度檔讀取，LINE 員工不需知道後端檔案位置，亦不需重新綁定。

**遷移期間**：原正式主檔已存在的 `打卡紀錄_歷史` 暫時保留不動。先清查現有資料，備份並驗證沒有遺漏／重複後，才決定搬到新年度庫；資料不可因同名表而直接覆蓋。

### C｜敏感資料服務（薪資單／特休帳務）

- **薪資資料獨立限制權限**：現有 Excel VBA 人資薪資仍作為核算來源。每月薪資正式確認並發放後，透過管理員授權、一次性匯出已核定**個人薪資單快照**到專用限制存取工作簿；不要直接把 Excel 原檔所有同事薪資／銀行帳戶給一般 LINE Web App。
- 員工 LINE 查薪資只能看**自己的**已發布月份，不能用前端傳員工 ID 改查別人的資料；本人身份由後端 LINE token 驗證及員工 ID 綁定決定。
- **特休剩餘數不是直接抓「請假申請」全部扣除**。需要來源為給假／到期／已核准特休／取消復回的完整異動流水，餘額可由台帳與每月結算快照比對。尚未結案申請可顯示「申請中（不計入已核准扣除）」等不同狀態。
- 薪資、特休查詢都先實作唯讀 API；薪資公布／更正只能管理者，且所有讀取及更正需有稽核紀錄。

## 既有已討論的人資規格（直接沿用，不重新決定）

- 每月 **5 日前完成上月結算**；主要雲端正式作業，每月底另做一份完整備份到公司電腦。封存完成與薪資計算完成是不同檢查點，不能只到每月 1 日便自動清除舊資料。
- 員工端維持 **LINE → LIFF 人資中心**，手機優先，不要求員工另外安裝獨立 App。每位員工只能查本人；薪資由管理者明確發布後才可查。兩位老闆各自使用自己的帳號，保有同等 OWNER 管理權限；但一般主管是否能看員工薪資須另獨立授權，不等於可核准請假就可看薪資。
- 人資目前仍有 Excel／VBA 薪資與特休模組。**特休以到職週年計算**，特休使用紀錄永久保留；原始時數可能為 3.5、3.5、8 小時等，不可在歷史來源提前四捨五入。特休顯示餘額可格式化，但後端計算須使用實際時數。
- 原本已有獨立 `特休管理.xlsm`／特休總表及年度出缺勤等 Excel 工作流程。薪資單對應的應給、已用、實際可用時數與可能的已折薪時數，需先對照現有表格欄位再建立 LINE 公布快照，不能擅自從請假申請加總替代。
- 假別固定六種：**事假、病假、特休、公假、婚假、喪假**，不得自動加入「其他」。
- 完整備份應包含出勤、請假、薪資、特休、員工基本資料快照、設定及資料結構；非只有打卡兩張表。

## 三、LINE 人員端與管理端

原本單一 LINE LIFF 保留主入口（登入一次、各頁共用同一已驗證員工身份）：

- **打卡**：上／下班狀態、執行中與成功回覆、斷線原請求 ID 查詢、今日紀錄。
- **出勤查詢**：預設當月＋前兩月；超過範圍的舊期若未開放給一般員工則由人資查詢，不能因歸檔就從系統消失。
- **補打卡／請假**：仍沿用原有申請及主管權限、歷史查詢；查詢可彙整當期／歷史，未結案與已結案分開表示。
- **特休**：年度給假、已使用、申請中、可用餘額、到期日、異動明細。
- **薪資**：已發布薪資單的年月選擇、核算項目及扣項；不顯示其他員工資料。
- **主管／人資**：C/D 接受文字通知、E 審核；員工自己不可利用變更請求參數提升權限。人資可查歷史及例外處理，但不能任意查所有人的薪資，需明確角色權限。

## 四、封存節點／查詢接口設計

### 建議以「月結」驅動，而不是每一天滾動刪除
以 2026-10-22 為例，前台預設可查 2026-08、09、10 月；7 月及更早已**完成月結**的資料進年度歷史庫。
- 月份歸檔資格＝早於當月＋前兩月的起始日 **且** 相應出勤、補卡、請假、薪資／特休已結案或具可追溯的修正機制。
- 尚未審核、將來才休的已核准假、尚未完成結算的舊月份，都不能只按申請建立時間直接搬掉。可留當期、同時保留可查的索引／待辦。
- 對同一月份的補審、更正應採**追加修訂紀錄／版本差異**，同步更新月摘要與特休／薪資關聯結果，不能默默改寫已關帳的原始歷史資料。
- 預設不建立新封存觸發器；先從目前原表做唯讀盤點，手動模擬單月成功並核對後，再開設**每月 5 日結算核對之後**的定時「檢查可封存月份」作業。該作業只針對**已核准月結**的月份封存，不能看到日期到了便自動刪列。
- 觸發器由公司打卡專用帳號持有、附執行失敗通知，並設封存紀錄與定期核對。

### 每個月封存批次採六步驟
1. 全量備份正式主表與既有歷史表，保留可復原版本。
2. 對來源取穩定、唯一且不可被重用的紀錄識別碼；舊紀錄若沒有穩定 ID，須先建立不會與前後批重複的對照規則，不可直接用列號當唯一鍵。
3. 使用 LockService 或等效一致性保護，先**寫入歷史庫**，驗證完整性（筆數、ID、日期、關聯、必要欄位）。
4. 登記「複製成功／待核對」；只在核對成功後，且擁有人確認可清除來源時才移除原表已封存明細。
5. 同一批次重跑不能重複搬入同一原始紀錄；中途失敗必須可以從 checkpoint 復原。
6. 重新以 LINE 測試帳號查詢「封存前／封存後」月份，驗證一致；如有錯誤先停止清除與回復。

Google Sheet 跨檔案不是原子交易，所以必須依上面「先寫後驗、允許安全重試」設計；不可假設兩個檔案在一個 transaction 自動一起成功。

### 統一查詢介面
- `myAttendance(month)`：優先查當期，依年月索引查年度歷史；若資料在交接期兩邊都有，必須用穩定 ID 去重，不能重複計算。
- `myLeaveHistory(period)`：狀態／是否仍有效需同時考慮當期申請及歷史更正。
- `myAnnualLeave(year)`：讀給假／已核准使用／調整流水，提供差額和來源月份，可對帳。
- `myPayslip(month)`：只讀已確認、已發布的個人薪資快照；當月未發佈時不得顯示其他員工或未確定金額。
- `managerArchiveAudit(month)`：僅管理者可讀封存批次與前後一致性差異，不回傳全體員工 GPS／敏感薪資。

已通過隔離 iPhone LINE 實機：上／下班與防重複、今日時間查詢、定位拒絕提示；歷史、特休、薪資的新查詢**都尚未真實部署、無實機驗證**。

已通過隔離開發 mock：原四頁復用、13 欄補打卡／12 欄請假、C/D 通知與 E 審核角色；但主管 LINE 通知可靠補送、薪資匯入、特休台帳完整性、跨午夜夜班、當期歷史兩端查詢尚未完成。

本輪設計**不會建立雲端新表、不會搬任何一筆資料、不會新增任何正式觸發器、不會影響原版工作流程**。先保住原始工作簿與 V2 實測成果，再分批做歷史查詢及敏感資料權限測試。
