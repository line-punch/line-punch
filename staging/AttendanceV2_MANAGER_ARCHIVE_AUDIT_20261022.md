# 2026-10-22｜現有主管通知審核與三個月打卡封存查核

**只針對使用者已做好的正式 LINE 打卡系統進行核對；不得把 V2 測試資料或新主管規則直接覆蓋正式內容。**

## 一、原有「審核通知名單」欄位與真實後端

依使用者提供的正式 Sheet 畫面及 2026-10-20 原始完整 Apps Script：
- A：員工 ID
- B：員工姓名
- C：通知主管 1（LINE userId），收到**文字通知**。
- D：通知主管 2（LINE userId），收到**文字通知**，C/D 相同時不重複送。
- E：審核主管（LINE userId），收到可核准／駁回的 Flex 卡片。
- 並非 C、D、E 都能核准；E 才是既有業務設定中的審核人。C 與 E 即使是同一個 LINE ID，也應視為「同時收通知與可審核」，不應以欄位位置自行取消任一用途。
- 讀取 `getManagers_` 及發送 `sendToManagers_` 與畫面設計一致。
- **原版 `handlePostback_` 收到動作後沒有重新檢查操作人等於 E 欄；亦未見來源簽章驗證。** 收到 E 專用按鈕不等於伺服器授權，因此 V2 必須在每次核准、駁回前，以 LINE 後端驗證身分＋E 欄比對，並維持 C/D 通知與 E 審核分流。主管權限名單不需重建。

已新增且只保留於隔離整合開發分支：
- `AttendanceV2_ReviewRecipients.gs` — 依 A:E 原欄位讀取 C/D 去重通知名單、E 唯一有權審核；沒有外送訊息或改表。
- `AttendanceV2_IntegratedSandboxDataService.gs` — 審核權限統一呼叫 `v2nCanApprove_`，比對後才允許更動模擬審核狀態。
- **後端模擬回歸 96／96 通過**，包含 C/D 只能通知、E 授權、重複設定與 E 空白時停止審核；尚未部署、未對真實主管發訊息。

## 二、原本三個月打卡資料封存

使用者原設計：
- `打卡紀錄`：保留最近三個月的工作記錄。
- `打卡紀錄_歷史`：超過留存期間的資料搬到此表，供後台與歷史查核，不應丟失。
- 既有 LINΕ 個人月查詢最多三個月，現正式前端 `queryAttendance()` 只查 `打卡紀錄`。

目前可確定：
- 使用者 2026-10-20 提供的 **1023 行**「LINE 打卡系統 完整覆蓋版」沒有出現 `打卡紀錄_歷史`，也沒有「封存／archive／自動搬移／排程建立」程式。
- 不排除真正目前的 Apps Script 另有 `.gs` 模組、另一個 project 或已安裝的觸發器；所以不能直接說功能沒運作，更不能聲稱已核對成功。
- 目前可讀到 Sheet 存在兩個分頁，但**尚無具有權限的正式資料表直接讀取**及正式 Apps Script 觸發器清單，因此正式資料筆數、最早／最新日期、是否按時封存皆尚未驗證。
- 不能在未備份及核對歷史表落地前，自動刪除 `打卡紀錄` 內的舊資料。

### 三個月截止日的兩種可能解釋
以 2026-10-22 為例：
1. 「當月＋前兩個日曆月」：2026-08-01 起保留於 `打卡紀錄`。
2. 「往前正好三個月」：2026-07-22 起保留於 `打卡紀錄`。

這兩種都可以用，只是不能不經確認就替換既有上線規則。現有個人月查詢是「當月＋前兩個月」，傾向 1，但不能因此認定既有封存器也採同樣邊界。

## 三、已準備無破壞唯讀查核，不等於已實地執行

- `AttendanceV2_ArchiveAuditReadonly.gs` 是**只讀稽核程式**，不能部署至既有 DATA TEST 專案或直接替換正式後端。
- 只在 `LINE打卡系統` 正式試算表綁定的 Apps Script 下，若擁有人**明確選擇執行**時，讀取兩張表 B 欄的日期，匯總最早／最新日期、分月筆數、保留區超過期限筆數、歷史表筆數、日期格式異常、兩種截止日。
- 另調用 `ScriptApp.getProjectTriggers()` 列出**同一 Apps Script 專案**已安裝的觸發函式名稱／型別。不能據此排除「另一個專案」有排程；排程存在也不代表真的搬移成功。
- 只輸出統計，**不輸出姓名、LINE userId、GPS、員工ID 等明細**。
- `AttendanceV2_ArchiveAuditReadonly.test.js` **12／12 項離線測試通過**，包含月界、日期異常、正確 project 檢查、觸發器權限不足及無寫入操作。
- 需由使用者授權／提供正式表可讀的查核結果或截圖後，才能判定實際歷史封存是否正常。此次沒有直接操作正式 Sheet 或其排程。

## 四、建議正式升級的封存安全規則

1. 先以唯讀方式確認當前與歷史資料之時間範圍及筆數，並確認哪個觸發器負責搬移。
2. 備份兩張表後再整合自動封存；只允許**早於指定截止日**的列搬移，不能因為請假、補打卡審核而忽略原始日期的資料。
3. 搬移採先寫歷史、再確認筆數及每筆識別，**確認成功才移除原資料**；若中斷，重新執行應不會搬第二份或遺失資料。
4. 正式打卡寫入與封存需避免競爭衝突／鎖定問題；更新後必須保有查詢與資料完整性。
5. 超過三個月的歷史應仍可供人資／管理員核對，不能一封存就使舊補打卡核定資料不可追溯。
